# Bug inspection: ECS module
- Date: 2026-11-22   - Scope: `void/include/ecs/*` (world, entity, query, sparse_set, pipeline, type_info, ecs_type, internal_component*, .inl) and `void/src/ecs/*` (world, entity, query, pipeline, ecs_type). One cross-module finding in `void/src/arena.cpp` because it breaks ECS startup.
- Reviewed commit/state: a2fec37 (clean tree, only `.claude/settings.local.json` untracked)
- Checklists used: review-ecs (items 1-12 walked through). Also read `dynamic_array.h`, `flat_hash_map.h`, `arena.*`, `utils.h` and `game_layer.cpp` (the only ECS consumer) to confirm behaviour.

## Summary
The ECS is in poor shape. Several core paths cannot work as written: scratch reset aborts at `World::startup`, `remove_type` always hits a ~32 GiB memcpy, the archetype column map is corrupted, and `world->set<T>` calls a null hook. The multithreaded pipeline can hang, and sync points silently drop deferred commands. Counts: S1 x4, S2 x12, S3 x12, S4 x1 (F29, grouping about 10 minor items). Most important: `Arena::pop_to` has an inverted assert, so `World::startup -> flush_deferred_cmds -> WorkerScratch::reset` aborts in every build (F1). Because of that, most later findings are only reachable once F1 is fixed. They were confirmed by static reading only, since nothing was built or run.

## Findings

### [F1] [S1-Critical] `Arena::pop_to` asserts the wrong direction, so every scratch reset aborts  (Confirmed)
- **Where:** `void/src/arena.cpp:99` (`Arena::pop_to`), reached from `void/src/ecs/world.cpp:42` (`WorkerScratch::reset`) via `world.cpp:117` and `world.cpp:1756`.
- **Problem:** `ENGINE_ASSERT(pos_ <= pos, ...)` is inverted. It should be `pos <= pos_`. This was added in the latest commit (a2fec37).
- **Scenario:** `World::startup` -> `init_pipeline_phase` builds entities with names, and `EntityBuilder::name` pushes into the scratch arena, so `pos_ > 0`. `startup` then calls `flush_deferred_cmds()`, which calls `reset()`, which calls `pop_to(0)`. The assert is `pos_ <= 0`, which is false, so the process aborts. The same happens at the end of every `tick()` (`end_defer`).
- **Suggested fix:** assert `pos <= pos_`. Check other `pop_to` callers, e.g. `ScopedArenaTemp::end_scratch`, which also pops to a smaller position.

### [F2] [S1-Critical] `TypeSet::init_remove` uses `this->count` (0), so every remove crashes  (Confirmed)
- **Where:** `void/src/ecs/ecs_type.cpp:243` (`TypeSet::init_remove`).
- **Problem:** `memcpy(ids + ridx, other->ids + ridx + 1, (count - ridx - 1) * sizeof(EntityId))` reads `count`, which is the destination's fresh 0. It should read `other->count`. `0u - ridx - 1` wraps to about 4e9, times 8, giving a ~32 GiB memcpy. `sort()` also runs before `this->count` is assigned (see F6).
- **Scenario:** `world->remove_type<Position>(e)`, `Entity::remove<T>()`, `EntityPatcher::remove_type<T>()`, or any `del_cmds` entry makes `get_or_create_archetype_remove` call `init_remove`. This is an access violation.
- **Suggested fix:** use `other->count - ridx - 1`, set `this->count` before `sort()`, and note that the result is already sorted so no sort is needed.

### [F3] [S1-Critical] `Archetype::init` writes the col-to-type half of `column_map` using a moved-from `tset.count` (0)  (Confirmed)
- **Where:** `void/src/ecs/ecs_type.cpp:124` (also `:88`).
- **Problem:** `type_set.move(..., std::move(tset))` sets `tset.count = 0`. Line 124 `column_map[tset.count + data_col_counter] = idx` therefore writes `column_map[col] = idx`, overwriting the type-idx-to-col half. The real second half `[type_set.count + col]` is never written and holds uninitialized memory.
- **Scenario:**
  - The non-builder paths (`move_archetype_{add,move,copy,remove}_op`) read `column_map[type_set.count + idx]` as `set_idx`. That value is garbage, or 0 on fresh zero pages. For 0, `assign_component<Position>(e, ...)` on an entity that already has `Name` moves `Name`'s bytes into the `Position` slot, or trips `type_set[set_idx]` out of bounds.
  - Separately, archetypes with a data-less type before a data type, such as `[Name, Phase(tag), X]`, get their tag's `-1` entry overwritten with a column index.
- **Suggested fix:** copy `type_set.count` into a local before the move, or use `type_set.count` after the move. Zero-fill `column_map`.

### [F4] [S1-Critical] `World::set_move` / `set_copy` call `hook.on_set` unconditionally  (Confirmed)
- **Where:** `void/src/ecs/world.cpp:1050` and `:1071`.
- **Problem:** `on_set` is null for every type registered via `component<T>()`. The `ECS_DEBUG` block that installed hooks is disabled, and `TypeHook()` zero-inits.
- **Scenario:** `world->set<Position>(e, Position{...})` or `Entity::set` calls a null function pointer.
- **Suggested fix:** `if (ti->hook.on_set)`. The same guard is used in the `move_archetype_*` ops.

### [F5] [S2-High] Sync-point flush runs while `deferred == true`, so commands are re-queued and then wiped  (Confirmed)
- **Where:** `pipeline.cpp:147` and `:172`, `world.cpp:1746` (`flush_deferred_cmds`), `world.cpp:456` (`resolve_entity_cmd`), `world.cpp:1763` (`tick`).
- **Problem:** `tick()` calls `start_defer()` and only clears `deferred` in `end_defer()`. `Pipeline::progress` calls `flush_deferred_cmds()` mid-tick. `resolve_entity_cmd` sees `deferred` and does `push_entity_cmd(std::move(command))` into the scratch. The loop keeps walking the old chain, then `reset()` sets `head = nullptr`.
- **Scenario:** system A defers `add_component(e, X)` or `create_entity(...)`, and a later conflicting system B is a sync step. At B's sync point every queued command is silently dropped. Only commands queued after the last sync reach `end_defer`.
- **Suggested fix:** set `deferred = false` for the duration of `flush_deferred_cmds` and restore it afterwards.

### [F6] [S2-High] `TypeSet::init_add/init_remove` sort before `count` is assigned, so type sets are unsorted  (Confirmed)
- **Where:** `ecs_type.cpp:228` and `:244` (`sort()` uses `count`, which is still 0).
- **Scenario:** an entity with `[Name(1), NPC(1004)]` gets `Position(1001)` added via `World::add_component` or a patcher. The new set is `[1, 1004, 1001]`. Consequences:
  - `search()` uses `lower_bound` and fails: `has_type`, `get`, `set` and queries report not found or assert.
  - `archetype_map` compares with memcmp, but the hash is order independent, so the same logical set can be stored under several archetypes.
  - `resolve_entity_cmd`'s merge loop assumes sorted sets and aborts with "Wrong add type".
  - Works by luck only when ids are added in ascending order, which is what the builder does.
- **Suggested fix:** set `count` first, or sort `ids` with an explicit count. Prefer an insertion that keeps the order.

### [F7] [S2-High] Deferred `remove_type` records the entity id instead of the type id  (Confirmed)
- **Where:** `world.cpp:1000` (`cmd.remove(this, eid)`; it should be `tid`).
- **Scenario:** a system on the pipeline calls `world->remove_type<Tag>(e)` while deferred. At flush, `get_or_create_archetype_remove(arch, eid)` asserts or crashes, or removes the wrong type.

### [F8] [S2-High] `assign_component(lvalue)` resolves `TypeId<T&>` (id 0)  (Confirmed)
- **Where:** `entity.h:143` and `:147` (`EntityMutator::assign_component`), `world.inl:165` and `:169` (`World::assign_component`). `World::set`, `assign_relationship` and the other `World` templates correctly use `TypeId<C>`.
- **Scenario:** `Position p; world->assign_component(e, p);` deduces `T = Position&`, and `TypeId<Position&>::s_id` is the never-registered 0. This hits `type_infos[0]` (an assert on a missing key) or `is_type_registerd(0)`.
- **Suggested fix:** use `TypeId<C>::id()` in both branches.

### [F9] [S2-High] `World::create_entity` returns a builder through a dangling reference to a destroyed temporary  (Confirmed)
- **Where:** `world.cpp:329` (`auto &builder = entity_builder().name(name).id(eid);`), then `:332-334`.
- **Problem:** the `EntityBuilder` temporary dies at the end of the full expression. `builder` dangles, and `add_relationship` and `std::move(builder)` read and write dead stack memory (~1 KiB of `EntityCommand` arrays).
- **Scenario:** `world->create_entity("x", parent)` is used by `game_layer.cpp:125`. Behaviour is UB, and in practice stack garbage is moved into the returned builder.
- **Suggested fix:** `EntityBuilder builder = entity_builder(); builder.name(name).id(eid); ...; return builder;`.

### [F10] [S2-High] Multithreaded `Pipeline::progress` can spin forever or loop forever  (Confirmed)
- **Where:** `pipeline.cpp:161-201`.
- **Problem (a):** `remaining` is set to `count` (number of systems), but each runner (`worker_dispatch + 1`) decrements it once. If `count > worker_count + 1`, `remaining` never reaches 0 and the main thread spins.
- **Problem (b):** `sync_point` is re-declared as 0 on every pass of the outer `while`. When `step.sync_point` is true at `current_step > 0`, the code sets `sync_point = current_step; break;` and runs the batch. On the next pass `sync_point` is 0 again, `current_step != 0`, so it breaks immediately with `count == 0`. `current_step` never advances, so this loops forever. With `count == 0`, `std::min(count - 1, ...)` also underflows.
- **Problem (c):** `batch->systems[count++]` has no bound check for the 128 limit (`world.h:15`), so a stage with more than 128 systems writes out of bounds.
- **Scenario:** a phase with more than `worker_count + 1` systems (more than 7 with `set_worker_count(6)`) hangs. Any stage where the second or later step is a sync step (two conflicting systems) hangs.
- **Suggested fix:** count only dispatched runners in `remaining`. Hoist `sync_point` out of the loop, or restructure so a sync step ends the batch and starts the next one. Bound `count` to 128.

### [F11] [S2-High] `Query_T::execute` on an uncached query accumulates duplicate results and double-frees  (Confirmed)
- **Where:** `query.cpp:130-137` (`QueryResult::clear`), `:155-168` (`execute`).
- **Problem:** `clear()` destroys each `MatchedArchetype` but never resets the array count (`archetypes.clear()` is not called). `execute()` runs `clear_result()` then `query_archetypes()`.
- **Scenario:** `query_builder<A>().each(cb)` returns a handle, and `handle.execute()` is called twice. The second call appends a second copy of every archetype, so the callback runs twice per entity. The third call calls `destroy()` again on already-freed `hi_*` arrays (`MatchedArchetype::destroy` does not null them), a double `vfree`. `QueryResult::destroy` at shutdown frees them once more.
- **Suggested fix:** `archetypes.clear()` after the destroy loop (and drop the explicit `~MatchedArchetype()`). Null the pointers in `MatchedArchetype::destroy`.

### [F12] [S2-High] `move_archetype_add_op` indexes the type set with the column index  (Confirmed)
- **Where:** `world.cpp:1355` (`src_arch->type_set.search(dst_arch->type_set[idx])`). It should be `[set_idx]`, as the move/copy/remove ops do.
- **Scenario:** `[Name, Phase(tag), Position]` has columns `[Name, Position]`. For column 1, `type_set[1]` is the tag. The code then looks up the wrong type in the source: it either moves the wrong data or default-constructs `Position`, overwriting existing data.

### [F13] [S2-High] Removing an entity's last component builds an empty `TypeSet`; `hash()` divides by zero  (Confirmed)
- **Where:** `ecs_type.cpp:166` (`h /= count`), `world.cpp:1290-1316` (`get_or_create_archetype_remove`).
- **Scenario:** an entity with a single type (`[Name]`) has it removed. The new set has `count == 0`, and `get_archetype(type_set)` calls `Hash<TypeSet>::Value`, which divides by zero. The `if (!dst_arch)` branch in `move_archetype_remove_op` is unreachable because `get_or_create_archetype_remove` never returns null. `TypeSet::operator==` also calls `memcmp` on null pointers.
- **Suggested fix:** map the empty set to `nullptr` in `get_or_create_archetype_remove`. Guard `hash()` against `count == 0`.

### [F14] [S2-High] Filter-callback signature mapping writes into the exec callback's array  (Confirmed)
- **Where:** `query.inl:286` (`exec_callback.sig_idx_to_term_idx[idx] = QUERY_ITER_ID;` inside `set_filter_callback`).
- **Scenario:** `.filter(+[](const QueryIter&, Position&){...})`. `filter()` runs before `each()`, so `exec_callback.sig_idx_to_term_idx` is still null, and this is a null write. If an exec callback was set first, it overwrites its mapping instead. The filter array entry stays uninitialized (read later by `get_filter_callback_arg`).
- **Suggested fix:** use `filter_callback.sig_idx_to_term_idx[idx]`.

### [F15] [S2-High] UP/CASCADE traversal stores the matched parent in the shared `QueryTerm`  (Confirmed)
- **Where:** `query.cpp:319` and `:379` (`term.valid_trav_target = target`), read in `query.inl:61-71` and `:117-124`.
- **Problem:** the target is per matched archetype, but the field lives in the single per-query term, so the last archetype visited wins.
- **Scenario:** children of parent P1 (archetype A1) and of P2 (archetype A2). A system with `up<ChildOf>` reads `world->get(valid_trav_target, ...)`, and every child sees whichever parent the last `add_if_match` stored. That is wrong data for all but one archetype. Store the target in `MatchedArchetype`, per term.

### [F16] [S2-High] `remove_entity` is not deferrable, and flushed commands are not validated  (Confirmed)
- **Where:** `world.cpp:431-452`, `:477` (`entity_records[command.eid]`, which asserts existence).
- **Scenario:**
  - A system calls `remove_entity(e)` during iteration. The immediate swap-back moves another entity into the iterated row (`eIdx < archetype->count` skips or double-visits entities), and the callback's references dangle. The skill checklist item 2 requires this to be deferred.
  - A deferred `add_component(e, X)` followed by an immediate `remove_entity(e)` makes the flush hit `entity_records[command.eid]` and abort.
  - `remove_entity` on an entity with `archetype == nullptr` also aborts, which is legitimate runtime input.
- **Suggested fix:** queue the removal in deferred mode. At flush, skip commands whose entity is gone (`is_entity_existing`).

### [F17] [S3-Medium] `revalidate_cached_query_entity_filter` computes the wrong rows and indexes with unsigned underflow  (Confirmed by reading; only for queries with `.filter`)
- **Where:** `world.cpp:1684-1692` and call sites (`world.cpp:684-693`, `:1386`, `:1470`, `:1554`, `:1635`), `query.cpp:75-91`.
- **Problem:**
  - ON_REMOVED copies `mask[count-1]` to `mask[affected_row]`. After `swap_back_entity`, `affected_row` is the old last index and the survivor's bit is at that old last index, so it reads the wrong slot and clears a live entity's bit.
  - If `count == 0` (last entity left the archetype), `count - 1` is `0xFFFFFFFF` and the `mask()` assert aborts.
  - In `resolve_entity_cmd` ON_ADDED runs before `++count`. When `row % 32 == 0`, `mask()`'s assert (`mask_idx < mask_count || eidx < count`) fails. `allocate_mask` is also sized from the pre-increment count, so the 257th entity has no `hi_entity_mask`.
  - `remove_entity` never revalidates.
  - `allocate_mask` leaves newly allocated `hi_entity_mask` words uninitialized.
- **Suggested fix:** pass the true removed row from before swap-back. Mirror the swap on the mask bits: `mask[row] = mask[last]; mask[last] = 0`. Allocate masks for `count + 1` on add. Zero-fill new words.

### [F18] [S3-Medium] Deferred command flush is LIFO and per-thread  (Confirmed)
- **Where:** `world.cpp:30-38` (`push_entity_cmd` prepends to `head`), `:1746-1757`.
- **Scenario:** a system queues `spawn(e)` then `add_component(e, X)`. The flush runs them in reverse, so the add happens before the spawn (assert on a non-existent entity). The scratches are also flushed worker-by-worker, so cross-thread order is arbitrary.
- **Suggested fix:** append at a tail pointer, or reverse the list before the walk.

### [F19] [S3-Medium] `resolve_entity_cmd` merge loop cannot handle mixed add+remove and duplicates  (Confirmed)
- **Where:** `world.cpp:586-667` and `:499-502`.
- **Problem (a):** when the types differ, `if (has_add_cmd)` is taken regardless of whether the difference is an add or a remove. A patch with both adds and removes hits `ENGINE_ASSERT(dst_tset_id == add_cmds[add_idx].tid)`. Once adds are exhausted, a remaining remove also trips `add_idx < add_count`.
- **Problem (b):** the builder and patcher never check "already has type". `init_add` with a duplicate id builds a set with a duplicate entry, and the same tid in both add and del is not reconciled.
- **Problem (c):** `if (src_archetype == dst_archetype) return;` returns without `command.destroy()` and without applying any assigned values. So `assign_component` of an existing component is a silent no-op, and a moved-in non-trivial value is leaked (its moved-to temp is never destructed).
- **Suggested fix:** advance by comparing ids and use the add or del list accordingly. Dedupe or reject duplicates in `EntityCommand`. Apply assigns when archetypes are equal.

### [F20] [S3-Medium] Relationship ids drop the target's version  (Confirmed)
- **Where:** `ecs_type.h:61-67` (`make_relationship` keeps only the low 32 bits). It is used in `world.cpp:488` (`register_relationship(..., high_32bit(cmd.tid), ...)`), `:406`, and `query.cpp:305`, `:307`, `:352`.
- **Problem:** `register_relationship` asserts `is_entity_existing(target_id)` with a versionless id. `get_parent` returns a versionless id, so `is_entity_existing(parent)` is false for any reused slot. `get_entity_archetype(target)` in `add_if_match` also asserts. A relationship pair also silently re-targets to a new entity that reuses the old slot, instead of dangling detectably.
- **Scenario:** destroy parent P (low id 300) and spawn Q, which reuses 300 with version 1. `entity_builder().parent(Q_id)` then aborts in `register_relationship`. Existing children of P now claim Q as their parent.
- **Suggested fix:** resolve the target to a full id with `entity_records.get_full_id(low)` before asserting. Decide on a policy for children when a parent is destroyed (cascade delete, or `remove_entity` strips the pairs).
- **Status: [PARTIAL]** Ids now resolve (user's changes). Stale-relationship policy is still open, recorded as `TODO(relationship-policy)` at `ecs_type.h:61`.

### [F21] [S3-Medium] `get_free_id` and explicit ids interact badly with the sparse set  (Confirmed by reading)
- **Where:** `world.cpp:355-365` (`is_existing` is version sensitive), `world.cpp:305-312`, `sparse_set.inl:128-173`.
- **Problem (a):** `get_free_id` uses version-sensitive `is_existing(next_id)`. If the live entity at that slot has a version above 0, it counts as free. `push` then asserts `!is_existing_skip_version(new_id)` and aborts.
- **Problem (b):** `create_entity(eid=300)` -> destroy -> `create_entity(eid=300)` pushes a second dense entry for the same low id (dead entries are not reused for explicit ids). Later a try-reuse hands out the stale entry while the page says occupied, so the assert `The id is already occupied!` fires.
- **Suggested fix:** use `is_existing_skip_version` in `get_free_id`. In `push`, with an explicit id, take over a matching dead dense entry.

### [F23] [S3-Medium] Systems' `T...` terms are always READ, and `need_sync` drops the syncing system's accesses  (Possible)

### [F25] [S3-Medium] Scratch arena is never reclaimed in immediate mode  (Possible)
- **Where:** `entity.cpp:52`, `world.cpp:1113` (`swap_back_entity` pushes a temp per column per swap), `WorkerScratch::push`.
- **Scenario:** a loader creates N entities outside `tick()`. Each `name()`, `assign_*` and swap-back temp consumes arena space, and the arena (16 MiB reserve) is only reset by `flush_deferred_cmds`. After enough entities, `Arena capacity exceeded` aborts.

### [F28] [S3-Medium] Pipeline/worker bookkeeping  (Possible)
- **Where:** `world.cpp:46-61`, `:169-185`.
- **Problem:**
  - `set_worker_count`: `max_worker_count == 0` makes `max_worker_count - 1` underflow. A second call appends more scratches. `worker_count == 0` with `multithread == true` makes `run_system`'s `% worker_count` a division by zero if ever dispatched.
  - `t_scratch_idx` is a class-level `thread_local` shared by all `World`s. Any thread other than the one that called `startup` (and not inside `run_system`) has index -1, so `worker_scratches[-1]` is an out-of-bounds access.

### [F29] [S4-Low] Smaller defects
- `SparseSet::destroy` iterates `idx <= alive_count` (off by one, reads a dead or out-of-range dense slot and `get()` asserts). `SparseSet::remove` calls `get(low_id)`, which asserts with a versionless id when `T` has a non-trivial destructor. Both are latent only while every `T` (`EntityRecord`, `Archetype`, `Query_T`, `TypeMetadata`) is trivially destructible. (`sparse_set.inl:292`, `:381`)
- `Archetype::resize`, `Archetype::init` and `OFFSET_ADDR(col.data, tm->size * row)` multiply two `uint32_t` values (`ecs_type.cpp:20`, `:122`, `world.cpp` many sites), so they overflow at 4 GiB per column.
- `QueryBuilderBase::each` ignores its `name` argument (`query.inl:546`) and `QueryBuilder::cache(EntityId)` ignores the id. `QueryTerm`'s `1 << queryTermIdx` with idx 31 is signed overflow UB (`query.inl:179`, `:199`, `:293`, `:313`). `term()` writes `desc.terms[cur_term_idx++]` before asserting, so it writes past the array at term 33 (`query.inl:347`).
- `World::get(...) const` calls the non-const `get` and will not compile when instantiated (`world.inl:256`).
- `Query`'s move-ctor hook casts `src` to `System*` (`world.cpp:146`). `Query` and `System` have a move hook but no copy hook, so `assign_component<Query>(const Query&)` aborts in `copy_to`.
- `EntityCommand()` leaves `mode` uninitialized (`entity.h:47`). The move-assign sets `other.eid` twice and does not release the destination's moved-in temps.
- `TypeId<T>::s_id`, `get_archetype_id()`, `get_query_id()` and `get_type_temp_id()` are process-wide statics, not per-`World` and not thread safe. A second `World` overwrites the first's type ids.
- `register_relationship` creates a throwaway named entity per relationship pair (wasting ids and never freed). It also holds `TypeInfo&` references across `type_infos.insert` in some callers (verified safe in the current call sites).
- `QueryHandle::destroy()` and `Query_T::destroy()` leave the archetype `tracked_queries`, `TypeInfo::tracked_queries` entries and the `cached_queries` slot behind. The next revalidation asserts, and `World::shutdown` would destroy the query twice. The handle's destroy is private and unused today, so this is latent. `World::shutdown` also calls `remove_entity` from inside `Query_T::destroy` before archetypes are torn down, which asserts if the user already removed the system entity.
- `TypeSet::search` with wildcard: a version-nonzero plain id with `high == 199` is treated as a wildcard. A plain type with the same low id as the relation can match.

## Edge cases not handled / untested
- Zero-term query (`query_builder<>().each`): `term_count = 1` with `tid == 0` (`query.inl:552-558`).
- More than 32 terms or 16 add / 16 del commands: bounds asserts abort at runtime (`entity.cpp:85`, `:133`) instead of returning errors. The `uint8_t` counts are fine.
- Archetype at `capacity` with `capacity == 0`, or `Archetype::resize` doubling to `uint32` overflow (`ecs_type.cpp:8`).
- Entity with no archetype (empty): `remove_entity`, `get_parent`, `has_type`, `get` all assert or null-deref.
- Component registered twice or with an id in `[1, 200)` that collides with the reserved list: `register_type_metadata` aborts via assert.
- `World::startup` twice or `shutdown` twice: `vallocator.init` and `destroy` are not guarded. Shutdown with `deferred == true` is not handled.
- Spawn plus add of the same type, add then remove of the same type in one command: undefined behaviour (F19).
- An archetype becoming empty and `entities[0]` being read (`pipeline.cpp:58`).
- A system registered during `tick()` (the pipeline is built once; `Pipeline::build_from_base_phase` is not re-run).

## Pitfalls & notes
- `ENGINE_ASSERT` is used for conditions that can legitimately occur at runtime: stale entity ids (`remove_entity`, `get_entity_record`, `set_child_of`), missing components (`get`, `set_*`), duplicate adds (`add_component`), and duplicate parent. All abort the process in every build.
- `FlatHashMap::operator[]` asserts on missing keys, so `type_infos[...]` on an unregistered relationship or type is an abort rather than a lookup failure.
- Component pointers (`get_mut`, `world->get`) die at any structural change, resize, or swap-back. No API enforces this.
- `TypeSet`'s hash is the sum of per-id hashes divided by the count. It collides easily, which is only a performance issue.
- Cross-World global state (type ids, archetype ids) makes running two worlds in one process unsafe.
- Conventions: `Query_T`, `QueryTerm` etc. mix PascalCase types with snake_case members, as the project expects. Some members lack the trailing `_` (`World` private fields, `EntityMutator::world`), and several `world.cpp` locals use camelCase (`destArchetype`, `addCmdCount`). Comments mention old PascalCase names.
- `World::World()` initializer list order differs from declaration order, and `system_batch` members (`count`, `systems`) are not initialized.

## Not reviewed
- `vallocator.*`, `flat_hash_map.h` internals (resize/Robin Hood), `job_system.*` thread-safety guarantees: only read to confirm assert and call semantics. In particular, whether `Vallocator::valloc` is thread-safe was not verified.
- `game_layer.cpp` and Win32 code outside ECS usage.
- Dead code per CLAUDE.md (`vulkan_junk.h`, stale `void/test/*`, empty `vulkan_renderer_api.*`) and the commented-out blocks inside `ecs/*.inl`.
- Nothing was compiled or run; all findings come from static reading.
